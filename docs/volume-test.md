> ## ⚠️ 이 문서의 숫자를 읽는 방법 — 먼저 읽을 것
>
> 측정 환경은 **개발용 macOS 노트북의 Docker Desktop VM** 이다. 프로덕션이 아니다.
>
> ```
> 호스트     : 12 코어 / 69 GB
> Docker VM  : 12 코어 / 8.32 GB      ← 호스트 램의 12% 만 할당
> VM 스왑    : 932 MB / 1023 MB 사용  ← 측정 시점에 거의 소진

>
> **VM 이 스왑을 거의 다 쓴 상태에서 측정했다.** OpenSearch 는 스왑되면 성능이 급락한다.
> 게다가 앱·MSSQL·수집기·OpenSearch·Dashboards·Loki·Grafana 가 **한 머신에 함께** 떠 있고,
> OpenSearch 는 **단일 노드 · 1 샤드**다. 프로덕션은 복수 노드로 샤드를 분산한다.
>
> 그래서 아래 숫자를 두 부류로 나눠서 읽어야 한다.
>
> ### 그대로 가져가도 되는 것 (하드웨어 무관)
>
> | 항목 | 왜 무관인가 |

> | 문서당 **224 bytes** | 스키마 + Lucene 인코딩의 함수다. 용량 산정에 직접 쓸 수 있다 |

> | indexing pressure = **힙의 10%** | 순수 비율. 절대 바이트만 힙에 비례한다 |
> | Loki 의 **과거 로그 거부** | 순수 설계 동작 |
> | **429 → 재시도 소진 → 청크 폐기** 메커니즘 | 설정이 만드는 동작. 하드웨어는 *언제* 걸리는지만 바꾼다 |
> | **DLS 오버헤드 ≈ 0** | 같은 하드웨어 안에서의 상대 비교라 유효하다 |

> ### 버려야 하는 것 (이 환경 전용)

> - 임계점 **100만 ~ 500만 건 사이**
> - 파이프라인 처리량 **17k ~ 71k/s**
> - 질의 응답시간 **절대값** (47ms 등)
>
> ### 절대 처리량은 이 머신에서 원리적으로 측정 불가다
>
> 단일 노드 · 1 샤드이므로 색인 처리량이 노드 수에 따라 늘어나는 프로덕션 특성을 재현할 수 없다.
> 절대 수치가 필요하면 **클라우드 VM 에서 재측정**하는 방법밖에 없다.
>
> 다만 **"설정이 원인인가 하드웨어가 원인인가"는 이 머신에서도 가릴 수 있다.**
> 하드웨어를 그대로 두고 설정만 고쳐 유실이 0% 가 되면 설정 문제이고, 안 없어지면 처리량 문제다.
> 그 실험은 이슈로 등록해 뒀다.

# 원인 분석

500만 건 단계에서 **34.65% (1,732,312건) 유실**이 발생했다. 원인을 분리했다.

## 1. 두 백엔드가 서로 다른 기본 한계에 걸렸다

둘 다 **설정값**이고, 아키텍처의 벽이 아니다.

### OpenSearch — indexing pressure (힙의 10%)

```
[error] [output:opensearch:opensearch.0] HTTP status=429 URI=/_bulk
"type":"rejected_execution_exception"
"reason":"rejected execution of coordinating operation
          [coordinating_and_primary_bytes=211788218, replica_bytes=0, all_bytes=211788218, ...]"
```

`211,788,218 bytes ≈ 202 MB`. 힙 2GB의 10%다.
OpenSearch 는 처리 중(in-flight) 벌크 바이트가 `indexing_pressure.memory.limit`(기본값 = 힙의 10%)를
넘으면 429 로 거부한다. **정상적인 백프레셔 동작이다.**

관측: 벌크 응답에 `rejected_execution_exception` 318회, 문서 단위로는 `index_failed: 3,655,650`.
`_cat/thread_pool/write` 의 `rejected` 는 0 — 스레드풀 큐가 아니라 메모리 압력 쪽에서 막혔다는 뜻이다.

### Loki — per-tenant 수집 속도 제한 (4 MB/s)

```
Ingestion rate limit exceeded for user fake (limit: 4194304 bytes/sec)
while attempting to ingest '1303' lines totaling '729410' bytes
```

이미지 기본 설정에 `limits_config` 가 아예 없어 기본값 **4 MB/s, burst 6 MB** 가 적용된다.
관측: Loki 429 **3,444회** — OpenSearch(159회)보다 **20배 이상 먼저, 더 많이** 막혔다.

## 2. 진짜 유실 원인은 429 가 아니다 — Fluent Bit 의 청크 폐기다

429 는 "잠시 뒤에 다시 보내라"는 신호다. 그런데 관측된 로그는 이렇다.

```
[error] [engine] chunk '1-1786525532.251354345.flb' cannot be retried: task_id=721, ... > output=loki.1
[ info] [engine] flush chunk '...' succeeded at retry 3: ...
```

- 재시도 3회까지는 성공하기도 했지만,
- 재시도 한도를 소진한 청크는 **`cannot be retried` 로 통째로 폐기**된다.

현재 설정의 문제는 두 가지다.

| 설정 | 현재 | 결과 |
|---|---|---|
| 버퍼 저장 방식 | **메모리** (`storage.type` 미지정 = memory) | 버스트를 흡수할 곳이 없다. 메모리가 차면 그대로 끝 |
| `Retry_Limit` | opensearch 출력 **미지정**(기본 1) / loki 출력 **3** | 백프레셔가 조금만 길어지면 폐기 |

즉 **유실은 백엔드가 못 받아서가 아니라, 수집기가 기다리지 않고 버려서** 생겼다.

## 3. 왜 100만 건은 무손실이었나

| 단계 | 생성 속도 | 파이프라인 처리량 | 유실 |
|---|---|---|---|
| 10만 | 122,692/s | 71,428/s | 0% |
| 100만 | 122,108/s | 54,054/s | 0% |
| 500만 | 89,909/s | 17,335/s | **34.65%** |

생성 속도는 세 단계 모두 비슷한데(약 9~12만/초) 파이프라인 처리량만 계단식으로 떨어졌다.
100만 건까지는 **버퍼가 버스트를 흡수**했고, 500만 건에서는 버퍼가 먼저 마른 것이다.

한계는 "초당 몇 건"이 아니라 **"버퍼가 흡수할 수 있는 버스트 총량"** 이라는 뜻이다.
이 환경에서 그 지점은 **100만 건과 500만 건 사이**에 있다.

## 4. 미검증 가설 — fan-out 간섭

Loki 가 OpenSearch 보다 20배 이상 많은 429 를 냈고, 두 출력은 **같은 Fluent Bit 입력 버퍼를 공유**한다.
따라서 "느린 Loki 때문에 버퍼가 차서 OpenSearch 경로까지 같이 무너졌다"는 설명이 가능하다.

**다만 이건 아직 가설이다.** 확인하려면 Loki 를 떼고 OpenSearch 단독으로 같은 500만 건을 돌려
유실률을 비교해야 한다. 그 실험은 하지 않았다.

같은 시간대에 관측된 부수 증상들도 이 가설과 방향은 일치한다.

```
[error] [output:loki:loki.1] could not flush records to loki:3100 (http_do=-1)     12회
[error] [upstream] connection #62 to tcp://172.19.0.5:3100 timed out after 10s      7회
[error] [output:loki:loki.1] no upstream connections available                       2회
[error] [upstream] connection #55 to tcp://172.19.0.2:9200 timed out after 10s       1회  ← OpenSearch
```

## 5. 별개 발견 — Loki 는 과거 시각 로그를 거부한다

`daysBack=3` 으로 과거 3일에 분산 생성했을 때:

| 백엔드 | 결과 |
|---|---|
| OpenSearch | `app-logs-2026.08.09` ~ `08.12` **4개 인덱스를 만들어 정상 수용** |
| Loki | **전량 거부** |

```
entry too far behind, entry timestamp is: 2026-08-10T21:06:00Z,
oldest acceptable timestamp is: 2026-08-12T07:58:57Z
```

Loki 는 스트림의 최신 시각을 기준으로 일정 구간보다 오래된 항목을 받지 않는다.
**수집기가 죽었다 살아나며 밀린 로그를 재전송하는 상황, 과거 로그 백필, 오프라인 고객사 서버의
버퍼링된 로그** 같은 시나리오에서 문제가 된다. OpenSearch 는 타임스탬프를 신경쓰지 않는다.

## 6. 질의 성능 — 이건 문제가 없었다

문서 436만 건 기준.

| 질의 | 계정 | 소요 |
|---|---|---:|
| `term company_id` 카운트 | admin | 47 ms |
| 전체 카운트 (**DLS 필터 적용**) | company1_admin | 50 ms |
| `event` × `outcome` 집계 | admin | 165 ms |
| 스택트레이스 조회 (**FLS 적용**) | company1_admin | 47 ms |

**DLS 오버헤드가 사실상 없다** (47ms → 50ms). 6만 건 시점에는 358ms 였는데 436만 건에서 50ms 로
오히려 빨라졌다 — 첫 측정이 캐시 미스였다는 뜻이고, DLS 는 필터 캐시에 올라간 뒤로는 공짜에 가깝다.

**회사별 격리를 켜도 성능 대가가 없다**는 것이 이 PoC 의 주장 2 를 뒷받침한다.

## 7. 문서당 크기 — 용량 산정 근거

| 단계 | 문서당 |
|---|---|
| 10만 | 231 B |
| 100만 | 224 B |
| 500만 | 224 B |

**224 bytes/문서** 로 수렴한다 (replica 0, 스택트레이스는 전체의 5%만 포함).

| 로그 건수 | OpenSearch 예상 용량 |
|---|---|
| 1천만 | 2.2 GB |
| 1억 | 22 GB |
| 10억 | 224 GB |

replica 1 을 두면 2배다. 실제 산정 시에는 스택트레이스 비율과 필드 추가를 반영해야 한다.

## 8. 이 측정으로도 답이 안 나온 것

- **Loki 를 떼면 OpenSearch 단독 유실률은 얼마인가** (4절 가설 검증)
- **무손실로 버틸 수 있는 지속 속도는 얼마인가** — `ratePerSec` 를 단계적으로 낮추며 찾아야 한다
- **파일시스템 버퍼로 바꾸면 500만 건 버스트를 흡수하는가**
- 1천만 건 이상 규모, 장시간(수 시간) 지속 부하
- 프로덕션 노드 사양에서의 절대 처리량
