# 원인 분석

500만 건 단계에서 **34.65% (1,732,312건) 유실**이 발생했다. 원인을 분리했다.

## 1. 두 백엔드가 서로 다른 기본 한계에 걸렸다

둘 다 **설정값**이고, 아키텍처의 벽이 아니다.

### OpenSearch — indexing pressure (힙의 10%)

```
[error] [output:opensearch:opensearch.0] HTTP status=429 URI=/_bulk
"type":"rejected_execution_exception"
"reason":"rejected execution of coordinating operation
          [coordinating_and_primary_bytes=211788218, replica_bytes=0, all_bytes=211788218, ...]"
```

`211,788,218 bytes ≈ 202 MB`. 힙 2GB의 10%다.
OpenSearch 는 처리 중(in-flight) 벌크 바이트가 `indexing_pressure.memory.limit`(기본값 = 힙의 10%)를
넘으면 429 로 거부한다. **정상적인 백프레셔 동작이다.**

관측: 벌크 응답에 `rejected_execution_exception` 318회, 문서 단위로는 `index_failed: 3,655,650`.
`_cat/thread_pool/write` 의 `rejected` 는 0 — 스레드풀 큐가 아니라 메모리 압력 쪽에서 막혔다는 뜻이다.

### Loki — per-tenant 수집 속도 제한 (4 MB/s)

```
Ingestion rate limit exceeded for user fake (limit: 4194304 bytes/sec)
while attempting to ingest '1303' lines totaling '729410' bytes
```

이미지 기본 설정에 `limits_config` 가 아예 없어 기본값 **4 MB/s, burst 6 MB** 가 적용된다.
관측: Loki 429 **3,444회** — OpenSearch(159회)보다 **20배 이상 먼저, 더 많이** 막혔다.

## 2. 진짜 유실 원인은 429 가 아니다 — Fluent Bit 의 청크 폐기다

429 는 "잠시 뒤에 다시 보내라"는 신호다. 그런데 관측된 로그는 이렇다.

```
[error] [engine] chunk '1-1786525532.251354345.flb' cannot be retried: task_id=721, ... > output=loki.1
[ info] [engine] flush chunk '...' succeeded at retry 3: ...
```

- 재시도 3회까지는 성공하기도 했지만,
- 재시도 한도를 소진한 청크는 **`cannot be retried` 로 통째로 폐기**된다.

현재 설정의 문제는 두 가지다.

| 설정 | 현재 | 결과 |
|---|---|---|
| 버퍼 저장 방식 | **메모리** (`storage.type` 미지정 = memory) | 버스트를 흡수할 곳이 없다. 메모리가 차면 그대로 끝 |
| `Retry_Limit` | opensearch 출력 **미지정**(기본 1) / loki 출력 **3** | 백프레셔가 조금만 길어지면 폐기 |

즉 **유실은 백엔드가 못 받아서가 아니라, 수집기가 기다리지 않고 버려서** 생겼다.

## 3. 왜 100만 건은 무손실이었나

| 단계 | 생성 속도 | 파이프라인 처리량 | 유실 |
|---|---|---|---|
| 10만 | 122,692/s | 71,428/s | 0% |
| 100만 | 122,108/s | 54,054/s | 0% |
| 500만 | 89,909/s | 17,335/s | **34.65%** |

생성 속도는 세 단계 모두 비슷한데(약 9~12만/초) 파이프라인 처리량만 계단식으로 떨어졌다.
100만 건까지는 **버퍼가 버스트를 흡수**했고, 500만 건에서는 버퍼가 먼저 마른 것이다.

한계는 "초당 몇 건"이 아니라 **"버퍼가 흡수할 수 있는 버스트 총량"** 이라는 뜻이다.
이 환경에서 그 지점은 **100만 건과 500만 건 사이**에 있다.

## 4. 미검증 가설 — fan-out 간섭

Loki 가 OpenSearch 보다 20배 이상 많은 429 를 냈고, 두 출력은 **같은 Fluent Bit 입력 버퍼를 공유**한다.
따라서 "느린 Loki 때문에 버퍼가 차서 OpenSearch 경로까지 같이 무너졌다"는 설명이 가능하다.

**다만 이건 아직 가설이다.** 확인하려면 Loki 를 떼고 OpenSearch 단독으로 같은 500만 건을 돌려
유실률을 비교해야 한다. 그 실험은 하지 않았다.

같은 시간대에 관측된 부수 증상들도 이 가설과 방향은 일치한다.

```
[error] [output:loki:loki.1] could not flush records to loki:3100 (http_do=-1)     12회
[error] [upstream] connection #62 to tcp://172.19.0.5:3100 timed out after 10s      7회
[error] [output:loki:loki.1] no upstream connections available                       2회
[error] [upstream] connection #55 to tcp://172.19.0.2:9200 timed out after 10s       1회  ← OpenSearch
```

## 5. 별개 발견 — Loki 는 과거 시각 로그를 거부한다

`daysBack=3` 으로 과거 3일에 분산 생성했을 때:

| 백엔드 | 결과 |
|---|---|
| OpenSearch | `app-logs-2026.08.09` ~ `08.12` **4개 인덱스를 만들어 정상 수용** |
| Loki | **전량 거부** |

```
entry too far behind, entry timestamp is: 2026-08-10T21:06:00Z,
oldest acceptable timestamp is: 2026-08-12T07:58:57Z
```

Loki 는 스트림의 최신 시각을 기준으로 일정 구간보다 오래된 항목을 받지 않는다.
**수집기가 죽었다 살아나며 밀린 로그를 재전송하는 상황, 과거 로그 백필, 오프라인 고객사 서버의
버퍼링된 로그** 같은 시나리오에서 문제가 된다. OpenSearch 는 타임스탬프를 신경쓰지 않는다.

# 2차 측정 — 환경 오염을 줄인 상태 (2026-08-12 18:25)

1차 측정의 숫자 중 어디까지가 하드웨어 탓인지 가리기 위해 **하드웨어는 그대로 두고 환경만 정리**했다.

| 조치 | 효과 |
|---|---|
| `mssql` / `dashboards` / `grafana` / `loki` 정지 | 자원 경쟁 제거 |
| Fluent Bit 을 OpenSearch 단독 설정으로 되돌림 | Loki 출력 실패로 인한 오염 제거 ([#3](../../issues/3) 격리 실험) |
| **VM 스왑 932 MB → 102 MB** | OpenSearch 가 스왑에 밀리지 않는 상태 확보 |

Docker VM 메모리는 **여전히 8.32 GB** 다 (상향하지 않았다).

## 결과

| 단계 | 1차 (오염 상태) | 2차 (정리 후) |
|---|---|---|
| 100만 유실률 | 0% | **0%** |
| 500만 유실률 | 34.65% | **20.47%** |
| 500만 실효 처리량 | 13,387/s | **46,453/s** |

> 실효 처리량 = 색인 건수 ÷ (생성 시간 + 색인 대기 시간).
> 1차 표의 "파이프라인 처리량" 은 대기 시간만으로 나눠서 2~7배 부풀려진 값이었다.
> 생성 중에 이미 색인된 분량이 분자에 남아 있었기 때문이다. 스크립트를 고쳤다.

## 결론 세 가지

### 1. 처리량은 환경이 지배한다 — 3.5배 차이

같은 하드웨어에서 **설정을 하나도 안 바꾸고** 실효 처리량이 13,387/s → 46,453/s 로 올랐다.
스왑 압박과 자원 경쟁만 제거한 결과다.

**따라서 1차의 처리량 수치는 전부 버려야 한다.** 그리고 2차 수치도 프로덕션 값이 아니다 —
단일 노드 · 1 샤드 · Docker VM 8.32 GB 라는 조건은 그대로다.

### 2. 그런데 유실은 사라지지 않았다 — 20.47%

이게 핵심이다. 환경을 정리해 처리량이 3.5배 올랐는데도 500만 건 버스트에서 여전히 100만 건이 샜다.

**즉 유실의 원인은 "느려서" 가 아니다.** 처리량이 46,453/s 로 충분히 빨라졌어도,
버스트 총량이 버퍼 용량을 넘으면 Fluent Bit 은 청크를 버린다.
[#1](../../issues/1) 의 진단(메모리 버퍼 + 낮은 Retry_Limit)이 하드웨어와 무관하다는 것을 뒷받침한다.

### 3. Loki 는 원인의 일부였지만 전부는 아니었다 — [#3](../../issues/3) 부분 답변

| 구성 | 500만 유실률 |
|---|---|
| OpenSearch + Loki 동시 전송 | 34.65% |
| **OpenSearch 단독** | **20.47%** |

Loki 를 떼자 유실이 **14.2 포인트 줄었다.** fan-out 간섭 가설은 **방향이 맞다.**
느린 백엔드가 공유 버퍼를 점유해 빠른 백엔드 경로까지 끌어내린다.

**다만 전부는 아니다.** 단독으로도 20.47% 가 남으므로, 근본 원인은 버퍼·재시도 설정이고
Loki 는 그 증상을 악화시키는 요인이다. 이 구분이 중요하다 — Loki 를 떼는 것이 해결책이 아니다.

## 부수적으로 확정된 두 수치

### 문서당 바이트 = 226 B (병합 후)

1차에서 224 B, 2차 중간에 310 B, 병합 직전 405 B 로 흔들렸다. 원인은 **세그먼트 병합 상태**였다.

| 상태 | 세그먼트 | 총 크기 | 문서당 |
|---|---:|---:|---:|
| 색인 직후 | 13개 | 2,014.5 MB | 405 B |

# 3차~최종 — 진짜 원인을 찾았다. 앞선 진단은 틀렸다.

## 먼저: [#1](../../issues/1) 의 진단이 틀렸다

2차까지의 결론은 "메모리 버퍼 + 낮은 `Retry_Limit` 때문에 청크가 폐기된다" 였다.
그래서 **파일시스템 버퍼 + `Retry_Limit False`** 를 적용하고 재측정했다.

| 구성 | 500만 건 유실률 |
|---|---|
| 2차 (메모리 버퍼, Retry_Limit 기본) | 20.47% |
| 3차 (**파일시스템 버퍼 + Retry 무제한**) | **30.25%** ← 오히려 악화 |

**가설이 틀렸다.** 그리고 이 실패가 진짜 원인으로 이어졌다.

## 계측을 넣자 바로 보였다

Fluent Bit 의 `HTTP_Server On` 을 켜고 `/api/v1/metrics` 를 봤다.
그때까지는 "앱이 만든 수 vs 색인된 수" 만 비교하고 있었는데, 그 사이에는
**Docker 로깅 드라이버 → Fluent Bit → OpenSearch** 라는 3개 구간이 있어서
어디서 샜는지 구분할 수 없었다.

메트릭을 보니 `storage_backlog` 에 **370만 건이 쌓인 채 전혀 줄지 않고** 있었다.
즉 3차의 "유실 30.25%" 는 **유실이 아니라 전송 대기**였다. 측정이 너무 일찍 포기한 것이다.

## 원인 1 — Fluent Bit 의 응답 버퍼 512KB (진짜 범인)

백로그가 왜 안 빠지는지 로그를 보니:

```
[warn] [http_client] cannot increase buffer: current=512000 requested=544768 max=512000
[warn] [output:opensearch:opensearch.0] http_do=-1 URI=/_bulk
[warn] [engine] failed to flush chunk ..., retry in 319 seconds
```

**`http_do=-1` 은 네트워크 오류가 아니었다.**
OpenSearch 가 돌려주는 **벌크 응답**을 담을 버퍼가 `Buffer_Size` 기본값 **512KB** 로 고정돼 있고,
응답이 그걸 넘으면 읽지 못해 실패로 처리한다. 벌크 응답에는 문서 한 건당 결과가 하나씩
들어가므로 청크가 커지면 응답도 같이 커진다.

**OpenSearch 는 색인을 정상적으로 마쳤는데(`index_failed=0`, `rejected=0`) 수집기만 실패로 알고 있었다.**

이 하나가 그동안의 증상을 전부 설명한다.

| 증상 | 실제 원인 |
|---|---|
| 초기 문서 중복 (5,000건 생성 → 9,210건 색인) | 응답을 못 읽어 재시도 → 이미 색인된 문서를 다시 색인 |
| "연결 수준 실패" 로 판단했던 `http_do=-1` | 연결은 멀쩡했다. 응답 읽기 실패였다 |
| 대용량 유실 | 재시도 소진 후 청크 폐기 (`Retry_Limit` 기본 1) |
| 재시도 대기가 89s / 125s / 319s 로 길어짐 | 지수 백오프. 측정이 그 사이에 포기 |

### 수정과 확인

```ini
Buffer_Size  False    # 응답 크기에 맞춰 버퍼를 늘린다
```

적용 직후 밀려 있던 백로그 **370만 건이 재시도 0 / 폐기 0 으로 즉시 전부 빠졌다.**

그런데 **색인 총계는 늘지 않았다.** 이미 색인돼 있던 문서들의 재전송이었고,
`Id_Key log_id` 덕분에 멱등 덮어쓰기가 됐기 때문이다.
→ **두 수정(`Buffer_Size`, `Id_Key`)이 한 번에 확인된 셈이다.**

## 원인 2 — Docker fluentd 드라이버의 링버퍼 1MB

`Buffer_Size` 를 고치고 깨끗한 조건에서 500만 건을 다시 넣었다.

```
생성   5,000,000
수신   4,194,493   ← Fluent Bit 이 받은 것
처리   4,194,493
색인   4,194,493
재시도 0    폐기 0
```

**Fluent Bit 은 하나도 버리지 않았다.** 받은 것은 전부 색인했다.
그런데 **805,507건(16.1%)이 Fluent Bit 에 닿기도 전에 사라졌다.**

`fluentd-async: true` 의 버퍼는 링버퍼이고 기본 크기가 **1MB** 다.
앱이 드라이버가 전달하는 속도보다 빨리 쓰면 넘치는 만큼 **조용히 버린다.**
앱에도 수집기에도 아무 기록이 남지 않는다.

```yaml
logging:
  driver: fluentd
  options:
    fluentd-buffer-limit: "268435456"   # 1MB → 256MB
```

## 최종 결과

| 구성 | 500만 건 유실 |
|---|---|
| 1차 — Loki 동시 전송, 메모리 버퍼, Retry 기본 | 1,732,312건 (34.65%) |
| 2차 — Loki 격리 | 1,023,574건 (20.47%) |
| 3차 — 파일시스템 버퍼 + Retry 무제한 | 1,512,382건 (30.25%) ※ 실제로는 전송 대기 |
| 4차 — **+ `Buffer_Size False`** | 805,507건 (16.1%) ※ 전부 드라이버가 드랍 |
| **최종 — + `fluentd-buffer-limit 256MB`** | **1건 (0.00002%)** |

```
수신   5,000,001
처리   5,000,001
폐기   0
재시도 1,429 (실패 0)
색인   4,999,999 / 5,000,000
```

### 남은 1건도 정체가 확인됐다

```
seq 범위: 2 ~ 5000000     ← seq=1 이 없다
```

**버스트의 맨 첫 줄 하나**다. `fluentd-async` 는 백그라운드로 연결을 맺기 때문에,
연결이 서기 전에 쓰인 첫 메시지가 버려진다. 이건 async 모드의 문서화된 트레이드오프이고,
"수집기가 죽어도 앱은 계속 돈다" 를 택한 대가다.

## 부수 관찰 — 버퍼를 키우면 앱이 느려진다

| `fluentd-buffer-limit` | 앱의 로그 생성 속도 |
|---|---|
| 1MB (기본) | 107,201/s |
| 256MB | 45,090 ~ 87,337/s |

버퍼가 크면 드라이버가 **버리는 대신 앱에 백프레셔를 건다.**
즉 `fluentd-buffer-limit` 은 **"로그를 버릴 것인가, 앱을 느리게 할 것인가"** 를 정하는 손잡이다.
`fluentd-async: true` 가 "앱을 절대 막지 않는다" 를 보장하는 게 아니라는 뜻이다.

## 이 결론이 하드웨어와 무관한 이유

두 원인 모두 **설정 기본값**이다.

| 원인 | 기본값 | 하드웨어 의존성 |
|---|---|---|
| Fluent Bit `Buffer_Size` | 512KB | **없음.** 벌크 응답 크기는 청크당 문서 수의 함수다 |
| Docker `fluentd-buffer-limit` | 1MB | **없음.** 앱 쓰기 속도 > 전달 속도면 어디서든 넘친다 |

빠른 하드웨어에서는 **더 큰 버스트를 줘야 재현될 뿐, 사라지지 않는다.**
클라우드·온프렘 어디에 배포하든 이 두 설정은 반드시 조정해야 한다.

## 교훈 — 계측 없는 진단은 추측이다

2차까지의 진단이 틀린 이유는 하나다. **"어디서 샜는지" 를 볼 수 없는 상태로 원인을 추정했다.**
`HTTP_Server On` 한 줄을 켜자 30분 만에 정확한 지점이 나왔다.

프로덕션 체크리스트에 넣을 것:

- [ ] Fluent Bit `HTTP_Server On` — 수신/처리/폐기/재시도 카운터를 상시 노출
- [ ] 그 값을 모니터링에 연결 — `dropped_records` 가 0 이 아니면 즉시 알림
- [ ] **앱이 만든 로그 수와 색인된 로그 수를 주기적으로 대조** — 이게 없으면 유실을 영원히 모른다
